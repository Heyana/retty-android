# Retty 长期工作管理规划

状态：设计草案。日期：2026-10-14。

用户在 Retty 里用一句话创建长期工作，随后持续查看进展、补充要求和处理问题。Retty 提供统一的产品入口，执行、循环、事件接入和会话尽量复用原生 Agent 或 LoopX 等现成工具。创建新的工作和管理已有工作使用同一份界面与关联模型。

第一版交付一条完整使用流程，先接一个后端、一种来源和一台执行主机。成本通过缩小接入范围控制，保留创建、执行、查看和干预的体验。

## 1 一条完整的使用流程

以用户输入“持续关注这个仓库的 Issue，判断值得处理的问题，完成修复与验证，需要决定时问我”为例：

1. 用户在当前项目选择“创建长期工作”，输入目标。项目目录、主机和已配置 Agent 自动带入。
2. Agent 整理出工作职责：看哪些来源、什么值得处理、如何验证、何时等待用户。缺少必需信息时，在这次对话中问清。
3. Retty 将工作交给已验证的原生执行入口，关联真实会话或原生任务，并读回创建结果。用户无需复制命令或手工建立循环。
4. 工作出现在列表中。用户可以看到目标、执行位置、当前活动或等待原因，以及最近结果，打开同一执行会话查看细节。
5. 用户补充“先处理 bug，暂时不要新增功能”，交给对应工作采用；界面区分已保存、待采用和已确认采用。
6. 需要用户判断时复用现有通知和会话输入；用户可以暂停后续处理、恢复或结束这份工作。

来源可以是 Issue、评论、协作消息、新文件或告警。第一版使用一种已接通来源验证这条流程，其他来源后续沿用相同产品形态。

## 2 创建与管理统一

每份工作记录其管理后端和原生身份。由 Retty 创建的工作保留用户描述与关联信息；已有的原生自动化通过后端提供的列举接口导入，或明确关联一个用户选择的原生工作。

列表按工作展示，用户不需要理解后端差异。可用操作由实际接入能力决定：能够原生创建、修改或停止的操作直接调用，缺少接口的操作打开对应原生会话完成，并展示确认结果。关联一条普通聊天不会自动把它标记为已运行的长期工作。

首版优先让一个后端的创建、查看和干预闭环成立。全量扫描所有工具、同步所有自动化类型不作为前置条件。

## 3 职责分工

| 能力 | 优先复用什么 | Retty 新增什么 |
| --- | --- | --- |
| 理解目标与生成工作方法 | 原生 Agent 的规划、文件和工具能力 | 创建入口，传递用户目标和已有项目上下文 |
| 循环执行与调度 | 原生循环、原生自动化或 LoopX 配套宿主 | 启动接入、原生身份关联与操作回读 |
| 读取和接收事件 | 已配置的 MCP、CLI、Channels 或来源工具 | 展示来源和缺失配置，关联对应工作 |
| 验证与总结 | Agent 的原生执行与项目检查要求 | 展示结果、产物和证据引用 |
| 长期目标与任务状态 | 所选后端已有的状态 | 读取和投影，保留来源和更新时间 |
| 终端、连接与介入 | Retty 现有会话服务、远端连接和通知 | 从工作导航到同一执行会话 |

Retty 保存工作定义、后端身份和展示缓存，不成为第二套调度或目标状态的权威。Agent 的一次回复完成，只能说明该轮结束，不能被展示成长期工作已经结束。

## 4 第一版后端与接入方式

首个候选是 Claude Code 原生循环，与 yetone 分享的使用方式一致。先做一个短的隔离能力试验：从应用发起创建，关联真实会话，观察下一轮，提交一次修改，并确认停止后不再自动处理。

Claude 文档提供会话内循环、调度、任务列举和取消机制，并说明会话与恢复限制；这些原生机制是否能被 Retty 可靠驱动，以试验结果为准。[原生循环与调度](https://code.claude.com/docs/en/scheduled-tasks)

试验通过后只实现一个适配器。它提供创建、读取和提交操作三个小范围入口，不先抽象多种执行宿主。用户的创建请求必须有可回读的原生结果，不能仅凭向终端写入文字就报告创建成功。

对新工作使用明确由 Retty 创建的专用会话，复用现有 PTY 管理。普通会话不被隐式接管。再次点击创建或重连时，根据已保存身份核对原工作，不重复启动。失败和身份不确定时展示未确认状态与打开会话的入口。

如果原生循环无法支撑这条使用流程，下一步直接验证 LoopX 现成入口能否完成相同流程。优先复用其工作区、CLI 合同和运行时集成；通过后采用其目标状态，不再自建一份目标系统。其 Custom Runner 合同仍需要宿主负责实际唤醒和会话，不能把这个接入成本忽略。[LoopX 接入指南](https://github.com/loopx-project/loopx/blob/main/docs/guides/custom-agent-runner-integration.zh-CN.md)

Codex 作为第二个后端，在第一个后端通过后增加。避免第一版同时验证两套生命周期、状态和控制语义。

## 5 工作定义与最小界面

一份工作保存稳定 ID、名称、用户目标、项目目录、主机、后端类型、原生身份和职责文档引用。职责文档由 Agent 生成和维护，记录来源、判断要求、方法与完成标准。已有后端配置直接引用原定义。

后端的工作状态与原生会话活动分别展示。例如“工作持续关注中”与“Agent 当前空闲”可以同时成立。只投影可确认的信息，显示来源和最近同步时间；无法读到下一次运行时间或当前状态时明确显示未确认，不从最后一条终端文本猜测。

第一版界面包含：

- 创建区：一句话目标，已有项目、主机和执行器配置。
- 工作列表：名称、目标摘要、执行位置、当前活动、等待用户和最近结果。
- 工作详情：职责、最近结果和产物、补充要求、暂停／恢复／结束、打开执行会话。

进度先复用可获得的生命周期与原生结果。若需要 Agent 生成进度摘要，按需或随工作段生成，不额外建立高频模型轮询。摘要属于执行者报告，测试或外部回读属于验收证据，界面保留这一差别。

手机先通过已有通知和对应执行会话查看、回答和介入。这是同一份工作的一条入口，首版不另做完整手机管理页。

## 6 修改与干预的生效

补充要求发送到记录中的原生身份。运行时支持实时输入就使用原生输入，支持轮次边界采用就显示待采用；不同时维护另一套自动续跑循环。

每份职责文档独立保存。多个工作共享项目时，不用同一个全局文件覆盖它们的不同职责。工作循环使用原生支持的方式重新读取自己的职责；编辑文件何时被采用必须在首个接入试验中验证。

暂停表示停止后续自动唤醒，当前轮是否中断由原生能力和用户选择决定。恢复原工作，结束则关闭该工作的循环。操作显示请求中、已确认或失败；不把“按钮点击成功”当作后端生效。

Agent 可以在已授权范围内调整方法、频率和下一步。用户目标与权限不因修改职责文档自动扩大。第一版复用后端的执行边界与权限机制，不建设通用自修改提案系统。

## 7 事件来源如何逐步增加

第一条工作流先使用一个已经可用的来源工具。需要检查变化时复用原生循环；需要实时到达时优先复用原生事件入口或来源已有的订阅工具。Claude Channels 提供向运行中会话推送外部事件的方向，但仍处研究预览，需验证当前环境的认证和插件能力。[Channels 文档](https://code.claude.com/docs/en/channels)

来源产生的新材料可以唤醒或补充同一份工作，并不要求每条消息创建一个新任务。由具体工作方法与后端承担关联和判断；Retty 展示其来源与处理结果。

多来源通过逐个增加已验证工具实现。第一版不建统一事件账本、通用规则引擎、跨平台游标或消息队列平台。需要离线不丢事件的业务，必须选择已经提供这种能力的来源与后端，或单独评估该来源的接入成本，不能仅凭原生循环给出可靠投递承诺。

## 8 开发范围与验证成本

首版只有四块新增工作：创建入口与工作记录，一个后端适配器，列表与详情，现有会话和通知的关联。继续复用原生循环、验收方法、来源工具和运行历史。暂停跨主机调度、自动崩溃续跑、多 Agent 编排、独立目标数据库、统一权限系统与大型规则编辑器。

开发顺序：

1. 做后端能力试验，确定一句话创建、身份回读、状态读取、修改和停止的可行入口。
2. 在现有会话能力上完成一句话创建并返回真实工作；重复请求与重连不重复启动。
3. 增加列表与详情，打通查看结果、补充要求、暂停和恢复。
4. 复用手机通知和会话导航，用一个真实来源完成验收。

只验证 Retty 新增的接入合同与一个完整业务流程：

| 场景 | 验收结果 |
| --- | --- |
| 一句话创建 | 生成职责并建立真实循环，用户不需要复制命令 |
| 新输入和无变化 | 原生工作能处理一次真实输入，无变化时保持等待或低频检查 |
| 持续查看 | 能区分循环存在、当前执行、等待用户与最近结果 |
| 补充要求 | 发往正确工作，有明确采用时间和回读结果 |
| 暂停 恢复 结束 | 原生后端实际生效，未确认时界面如实显示 |
| 退出 GUI 重开 | 复用存活会话与工作，重复点击不会启动第二份 |
| 操作失败与断开 | 保留关联，显示未确认，不把失败操作报告为成功 |

后端内部的通用故障矩阵沿用其既有能力；Retty 只测试自己新加的接口、重复请求与结果确认。全部使用隔离目录、测试来源和专用会话，构建设备操作遵循 [development.md](development.md)。

首个后端无法完成创建和干预闭环时，暂停界面扩展，验证其他现成后端。不能把失败降级成提示词收藏后宣称已经交付长期工作管理，也不能直接转向自建整套执行平台。工期在短接入试验后，按已确定的四块工作估计。
